## 1. Outcome and implementation scope

The outcome is **one native contract owner for threetched functionality**, projected through our existing filesystem and admission path. A native operation should not have separately authored schemas under `threetched`, `tched_router`, `large_language_model` or another name.

Start with a coherent, useful slice: finish the direct plugin/skill-wrapper consolidation, then migrate additional proven overlaps as their required contracts and callers are understood. Capture only the native contracts needed for the selected slice. Complete the affected source, callers, generated artifacts, mount selections and release catalog together. Do not turn the first slice into a prerequisite to implement every native tool, persona, workflow or memory feature.

For each existing behavior, explicitly select one disposition:

- **Migrate now:** native counterpart established; implement its canonical contract and update callers.
- **Keep as an integration responsibility:** identity admission, scoped context, committed-state publication or receipts still belong to our system. This does not justify independently redefining the native operation.
- **Defer:** record the missing feature and caller impact on the existing task board. Do not expose a fake-success operation or claim parity for deferred behavior.
- **Retire:** remove the declaration and reconcile its callers/policy references; document the resulting feature change.

Removing duplicate declarations is not itself a reason to move or delete authoritative data. Preserve existing principal/session partitions and Cozo data. A compatibility name, if temporarily necessary for a demonstrated caller, must resolve to the one canonical declaration and admission path; it must not become another independently authored plugin schema or permanent wrapper layer.

## 4. Native capture and the schema-to-blob boundary

The present implementation is:

1. Explicit `opblob` sealing calls `threetched::prepare_schema_capture`.
2. The selected binary/manifest are checked; the capture reads native `config schema`, recursive command `--help`, version and binary digest.
3. `schema_from_capture` derives the threetched PluginSchema. Separately registered handwritten plugins still produce their own PluginSchemas.
4. `opblob` seals each full PluginSchema into the blob catalog. Full reseal removes plugin IDs absent from the build.
5. Golden preparation stages the already sealed catalog; snapshot send/receive and activation transport it. FUSE projects the resulting declarations and committed state.

Evidence: [explicit sealer][E13], [capture owner][E14], [CLI capture implementation][E15], [full-schema blob serialization][E16]. Duplicate authoring enters **before sealing**; a shared catalog alone does not remove it.
