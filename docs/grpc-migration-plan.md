# Tonic 0.12 → official `grpc` crate: migration plan

Status: **phase 1 done (tonic/prost family on 0.14 workspace-wide, builds); phase 2 started (opt-in `grpc-preview` feature in op-grpc-bridge).** Rebased onto dev `be41132`. Per-occurrence Jev review: docs/tonic-occurrence-review.md.
Date: 2026-11-18. Toolchain on antix1: rustc/cargo 1.100.0. Host protoc: 3.21.12 (Debian).

## What `grpc` 0.9.0 actually is (checked against the published crate source)

| Item | Finding |
|---|---|
| Crate | `grpc` 0.9.0 on crates.io, published 2026-05-28 by the grpc/grpc-rust project (the old stepancheg `grpc` 0.8.x is a different, dead codebase under the same name). |
| Maturity | README: "This version is a preview and not recommended for any production use. All APIs are unstable." |
| MSRV | 1.88 (antix1 has 1.100 — fine). |
| Hard deps | `tonic ^0.14.6` (feature `codegen`), `hyper 1` (client, http2), `http 1`, `tower 0.5` (optional, default on), `rustls 0.23` + `tokio-rustls 0.26` + `rustls-platform-verifier 0.6` (default `tls-rustls`), `hickory-resolver 0.25` (default `dns`), `socket2 0.6`, `tokio 1`. |
| Public API | `grpc::client` (`Channel::new(target, creds, ChannelOptions)`, `Invoke` trait, `SendStream`/`RecvStream`, interceptors, load balancing, name resolution `dns:`/`unix:`), `grpc::credentials` (`LocalChannelCredentials`, rustls), `grpc::metadata` (with `From`/`TryFrom` for `tonic::metadata::MetadataMap`), `grpc::core` (`SendMessage`/`RecvMessage`, `RequestHeaders`, `Trailers`), `grpc::Status` (= `Result<(), StatusError>`). |
| Server | `grpc::server` is **`pub(crate)`** — there is **no public server API** in 0.9. |
| Transport | The client uses **tonic 0.14 internally** as its HTTP/2 transport (`client/transport/tonic`). |
| Codegen | `protoc-gen-rust-grpc` + `grpc-protobuf` + `grpc-protobuf-build` target **Google's `protobuf` v4 crate (4.34)**, not prost; need cmake and a modern protoc. |
| Missing vs tonic | No tonic-web, reflection, health service, server interceptors, server TLS, `transport::Server`. |

### Do Tonic-generated services work with it?
* **Server side: no direct use** — grpc 0.9 cannot host anything; tonic-generated `*Server` types keep running on `tonic::transport::Server`.
* **Wire level: yes.** A `grpc::client::Channel` can call any tonic-served method. Proven in this worktree:
  `op-grpc-bridge/src/grpc_preview.rs` adapts prost messages to grpc's `SendMessage`/`RecvMessage`
  (no extra codegen) and its test calls a tonic 0.14 `tonic-health` server through a grpc `Channel`.
* **Generated client stubs: no.** Tonic-generated `*Client<T>` need `T: tonic::client::GrpcService`; `grpc::client::Channel` implements grpc's `Invoke`, not that trait.
* Since grpc 0.9 itself depends on tonic 0.14, the realistic path is "tonic 0.14 everywhere, grpc alongside for client paths", not "remove tonic".

## Phases

### Phase 1 — tonic 0.12 → 0.14 family (prerequisite; required by grpc 0.9) — DONE
* Workspace: `tonic 0.14` (`tls` → `tls-ring`, `tls-roots` → `tls-native-roots`, `tls-webpki-roots` kept), `tonic-web/-reflection/-health 0.14`, `prost`/`prost-types 0.14`, `prost-reflect 0.16`, new `tonic-prost 0.14`, `tonic-prost-build 0.14`, `grpc 0.9` (workspace entry only).
* Every `build.rs`: `tonic_build::configure()` → `tonic_prost_build::configure()`; op-chat `.compile()` → `.compile_protos()`; op-chat drops its private `tonic-build 0.11`/`prost-build 0.12` pins.
* Every crate with codegen gets the `tonic-prost` runtime dependency (generated code calls `tonic_prost::ProstCodec`).
* op-services / op-cognitive had private 0.12 pins → moved to 0.14.
* `tonic_web::enable(svc)` (removed) → `.layer(tonic_web::GrpcWebLayer::new())` (op-cache).
* op-chat's checked-in generated files (`src/orchestration/proto/*.rs`) are regenerated by its build.rs.
* op-web `door_proxy.rs`: `tonic::body::boxed(b)` → `tonic::body::Body::new(b)`.
* op-grpc-bridge `server.rs`: tonic 0.14 router (axum 0.8) is finished with CORS + 404 fallback, then mounted via `fallback_service` under an axum 0.7 router that keeps `/mqtt`.

### Phase 2 — `grpc` alongside, opt-in (STARTED, op-grpc-bridge only)
* `op-grpc-bridge` feature `grpc-preview` → optional `grpc` + `bytes`; module `grpc_preview` (prost adapter, `local_channel()`, `unary()`), with an interop test.
* Next candidates (client-only call paths): op-mcp `grpc/client.rs`, op-chat `grpc_pool.rs` (currently a TODO stub), op-xray-daemon `commander_client.rs`, op-web `door_proxy.rs` (needs TLS → grpc rustls creds), bridge `grpc_client.rs`. Each needs streaming support in the adapter and a decision on TLS creds.

### Phase 3 — wait for upstream
* Server, reflection, health, grpc-web, interceptors stay on tonic 0.14 until grpc-rust publishes a public server API.
* Re-evaluate codegen when grpc-protobuf supports prost or when moving to protobuf v4 is acceptable (needs newer protoc than Debian's 3.21 and cmake).

## Risks
* **Preview crate**: grpc 0.9 APIs are unstable; keep it behind `grpc-preview` and out of default builds/deploys.
* **tonic-web**: `enable()` removed → layer; grpc-web CORS behaviour should be re-tested from the browser UI.
* **reflection/health**: 0.14 bumps prost-types; descriptor sets still produced by tonic-prost-build — re-run live reflection probes.
* **TLS features renamed**; `tls-ring` chosen to keep the ring provider. op-grpc-bridge dev-deps use `rustls` with aws_lc_rs — two providers may need explicit `CryptoProvider::install_default` in tests.
* **prost-reflect 0.16 / prost 0.14** across op-plugins, op-blob, dynamic codec — API mostly the same; watch `DynamicMessage` encode/decode signatures.
* **Multiple prost versions** remain if any third-party crate still pins prost 0.12/0.13.
* **axum**: tonic 0.14's router uses axum 0.8 while the workspace uses axum 0.7; fine as long as tonic routes are not merged into axum 0.7 routers.
* **protoc 3.21** on host: fine for tonic-prost-build; too old for grpc's protobuf-v4 codegen.
* **op-chat checked-in generated code**: regenerated output is large; review as generated.
* **Deploy**: nothing here changes the running bridge (pid 26745) — new binaries need a separate, approved rollout.
